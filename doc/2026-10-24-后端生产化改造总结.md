# 2026-10-24 后端生产化改造总结

> 目标：支持单机 Docker Compose + Nginx 部署下 10,000 人同时在线聊天（10k 在线 ≈ 同时活跃对话 5-10%）。

## 一、P0 稳定性改造

### 1. SSE 流式接口重构（`chat.py`）
- **心跳保活**：请求建立后立即发送首字节 ping，之后每 15s 发送 `: ping` 注释帧，防止 Nginx/客户端在 LLM 首 token（最长 60s+）前超时断开。
- **断连检测**：循环内检查 `request.is_disconnected()`，客户端断开后取消 LLM 任务，不再白白跑完整链路。
- **单轮硬超时**：整轮处理 90s 超时（`asyncio.wait_for`），超时取消任务并推送规范化 error 事件。
- **错误兜底**：`traceback` 不再外泄给客户端，只写日志；SSE 错误统一为 `{code, message, retryable}` 结构。

### 2. LLM 并发控制（新增 `src/core/concurrency.py`）
- 全局 LLM 信号量（默认 200/进程，可配 `LLM_MAX_CONCURRENCY`），排队等待超阈值抛 `SystemBusyError` → 429。
- `guarded()` 包装：信号量 + `asyncio.wait_for` 超时，Supervisor / 问诊图 / 4 个 worker agent 全部接入。
- 附带 `llm_in_flight()` 在途计数，供 `/metrics` 暴露。

### 3. 数据库 / Redis / httpx 连接池调优
- `database.py`：连接池 `pool_size=30, max_overflow=20`（单进程峰值 50，双 worker = 100，PG `max_connections=200` 留余量），`pool_pre_ping` + `pool_recycle=5min`。
- `redis_cache.py`：两连接池增加 `max_connections=200`、`socket_timeout`、`health_check_interval`，Redis 栈异常不再拖垮请求。
- `config.py`：httpx 客户端（trust_env=False 直连）显式 `Limits(max_connections=400, max_keepalive_connections=100)`，解除默认 100 连接对 LLM 吞吐的封顶。

### 4. DB 会话解耦
- `chat_stream` 端点不再 `Depends(get_db)` 全程持有 AsyncSession；DB 会话改为**短作用域**按需创建，SSE 长连接不再占用连接池。

### 5. Worker 降级兜底（`worker_tools.py`）
- 4 个 worker agent（报告/药物/知识/运营）调用加 try/except，LLM 失败返回友好降级文案，不再把异常冒泡给用户。
- `call_inquiry_agent` 补传 `db_session` 与 `callbacks`（修复患者上下文加载失败、用量漏记）。

### 6. 顺带优化（`agents/inquiry/graph.py`）
- `MilvusClient` 改为进程级复用（`lru_cache`），不再每条消息新建 gRPC 连接。
- StateGraph 编译缓存方案**已回退**（图编译闭包持有 deps/db_session，缓存会导致会话串扰）。

## 二、P0 安全改造

### 1. JWT 鉴权接入聊天接口（聊天为"可选登录"，其余强制）
- 新增 `src/api/deps.py`：`get_current_user_id()` 强制登录、`get_optional_user_id()` 可选登录；两者都**只从 token `sub` 取 user_id**，不信任请求体自报（杜绝越权读写他人会话）。
- `/api/v1/chat`、`/api/v1/chat/stream`：**未登录也可聊天**（游客模式），带合法 token 则识别患者身份；token 非法/过期仍返回 401（不静默降级为游客，避免登录态失效后丢失历史）。
- `/api/v1/chat/stream/pending`、`/api/v1/sessions*`：强制鉴权（游客无历史记录）。
- 游客与登录用户的差异见「九、游客模式与患者身份兜底」。
- `auth.py` 的 `_issue_token` payload 增加 `sub` 字段（鉴权依赖契约）。

### 2. JWT 密钥环境化（`jwt_utils.py`）
- 删除硬编码 SECRET_KEY 与 print 泄露 token 的问题代码；`SECRET_KEY` 改读环境变量（`JWT_SECRET_KEY`），生产环境未配置拒绝启动。

### 3. 会话级互斥锁
- 同一 `user_id:session_id` 并发消息用 Redis `SET NX PX 30s` 抢锁，未抢到返回 409"处理中"，消除 read-modify-write 竞态交叉覆盖 InquiryState 的问题。

### 4. 其他
- CORS 环境化（`CORS_ORIGINS` 逗号分隔配置，替换硬编码 localhost）。

## 三、P1 消息持久化

### 1. 新表（`src/modules/chat/model.py` + alembic 迁移 `b5e2f7a91c03`）
- `conversations`：`(user_id, session_id)` 唯一，标题、最后 seq 游标、活跃时间。
- `chat_messages`：会话消息明细（role、content、event_type、seq、client_message_id、turn_id），唯一索引 `(session_id, client_message_id)` 支持幂等 upsert。

### 2. 批量落库队列（新增 `src/core/persist_queue.py`）
- 进程内 asyncio.Queue + 单 consumer：50 条或 500ms 攒批，批量 upsert 入 PG；失败退避重试，不阻塞主链路。
- 消息在 SSE 事件产出时投递到队列，**PG 为 source of truth**，Redis 状态只作热缓存。

### 3. token_usage 队列化（`llm_callbacks.py`）
- 修复 `asyncio.create_task` 无引用被 GC 导致的偶发丢数据；
- 由"每次 LLM 调用新建 DB session"改为投递到 persist_queue 攒批写入，10k 并发下不再打爆连接池。

## 四、P1 幂等与限流

### 1. 消息幂等
- `ChatRequest` 新增 `client_message_id`（前端生成 UUID）；
- Redis `SETNX chat:idem:{user_id}:{client_message_id}`（5 分钟窗口）：重复提交直接重放上次回复，不重跑 LLM；
- 落库 upsert 依赖唯一索引二次兜底。

### 2. 接口限流（新增 `src/middlewares/rate_limit.py`）
- Redis 滑动窗口：按用户 30 msg/min（可配），超限 429 + `Retry-After`。

### 3. 连接层限流
- 进程内 SSE 并发计数器（`sse_limiter`，上限 `SSE_MAX_CONNS=4000/进程`），超限 503 + `Retry-After: 5`；
- Nginx 侧 `limit_conn`/`limit_req` 双层防护（见部署）。

## 五、P1 断线重连

- SSE 每个业务事件携带 `id: {seq}`（会话内递增，Redis `INCR` 维护）。
- 新增 `GET /api/v1/chat/stream/pending?session_id=&after_seq=`：客户端重连后增量拉取未送达消息（含最新 `seq` 游标）。
- 会话游标同步持久化到 `conversations.last_seq`，Redis 丢失后仍可恢复。

## 六、部署形态（`Dockerfile` + `his-agent-platform-docker/`）

### 1. 应用镜像（根目录 `Dockerfile`）
- 多阶段构建、非 root 运行、uvloop + httptools；
- `CMD`: `uvicorn src.main:app --host 0.0.0.0 --workers 2 --loop uvloop --http httptools`。

### 2. docker-compose 升级
- 新增 `app1` / `app2` 双副本服务（共享 `tiangong-net`）；
- 新增 `nginx` 服务，挂载 `nginx/nginx.conf`；
- PG 命令追加 `max_connections=200`；Redis 追加 `--maxmemory-policy noeviction`（防状态被逐出）；
- 基础设施容器增加 CPU/内存资源限制。

### 3. Nginx 配置（`nginx/nginx.conf`）
- SSE 关键参数：`proxy_buffering off`、`proxy_cache off`、`proxy_read_timeout 300s`、`chunked_transfer_encoding on`；
- `limit_conn`（单 IP 连接数）+ `limit_req`（请求速率）；
- upstream 指向 app1:8000 / app2:8000，普通轮询即可（**已核实进程内无会话本地状态**——LangGraph 状态在 Redis checkpointer、业务状态在 Redis/PG，无需 sticky session）。

## 九、游客模式与患者身份兜底（2026-10-24 追加）

### 1. 游客（未登录）可聊天，但不留痕

| 能力 | 登录用户 | 游客（未登录） |
| --- | --- | --- |
| 聊天 / 问诊 / 报告解读 | ✅ | ✅ |
| 会话级短期记忆（Redis，1h） | ✅ | ✅ |
| 新建会话 | ✅ | ❌（前端按钮拦截 + 后端不建会话） |
| 会话/消息落库、历史列表 | ✅ | ❌ |
| 长期记忆（save/search_memory） | ✅ | ❌（工具直接返回"未登录"） |
| 问诊记录、挂号记录落库 | ✅ | ❌（`InquiryDeps.persist=False`） |
| 查询个人档案 | ✅ | ❌（提示登录，不查库） |

实现要点：
- `chat.py`：`ChatIdentity`（user_id / authenticated / rate_key / patient_id）；游客 `user_id="anon"`，`thread_id="anon:{session_id}"`（患者 ID 为纯数字，永不冲突），会话之间仍按 session_id 隔离。
- `_persist_message(persist=False)`：只递增 Redis `chat:seq`（供 SSE `id:` 断线续传），不建 `conversations`、不写 `chat_messages`。
- 限流维度：登录 `user:{id}`、游客 `ip:{ip}`。
- 问诊链路：`run_inquiry(user_id=None)` + `build_inquiry_deps(persist=False)` 跳过问诊记录落库；`handle_handoff(persist=False)` 跳过挂号落库，并在回复末尾提示"本次为未登录咨询，预约信息不会被保存"。

### 2. 患者身份问答兜底（"我是谁"）

- 新增工具 `src/tools/patient_tools.py::get_my_profile`：按当前登录患者 ID 查 `patients` 档案（姓名/性别/年龄/血型/过敏史/既往史/脱敏手机号与身份证）。
- Supervisor 提示词规定取数顺序：`search_memory`（长期记忆）→ 无身份信息时 `get_my_profile`（数据库兜底）→ 游客则如实告知登录后可查，**禁止编造**。
- `UserContext` 扩展 `authenticated` / `patient_id` 字段，工具据此判断是否可查库。

### 3. 顺带修掉的两个线上问题

- `_event_generator` 缺少 `request` 参数（原先 15s 无 token 事件时触发 `NameError`，问诊等长链路 SSE 必断）→ 已补参数，心跳正常。
- 限流器 `rate_limit.py` 未 `await get_redis_client()`（协程未等待导致限流失效、每次 fail-open）→ 已修，限流恢复生效。
- `TURN_TIMEOUT` 由 90s 调整为 150s：问诊一轮含 3-6 次串行 LLM 调用（单次约 10s，诊断结论更慢），90s 会误杀正常问诊。

**本次实测（本机 Redis/PG/Milvus 均在线）**：
- 游客发"你好"→ 正常流式回复；`conversations` / `chat_messages` 仍为 0 行（确认零落库）。
- 游客问"我是谁"→ 明确回复"游客（未登录）状态，无法查询个人档案"，未编造身份。
- 登录用户（患者 ID=1）问"我是谁"→ 先 `search_memory` 无结果，再 `get_my_profile` 命中档案，回复"张晓晓 / 男 / 12 岁 / 188****2222"。
- 无 token 请求 `/api/v1/sessions` → 401；登录用户消息正常落库（会话 + user/assistant 消息）。
- `alembic upgrade head` 已执行（c7e2a9f41b30 → b5e2f7a91c03），`conversations`/`chat_messages` 建表完成。
